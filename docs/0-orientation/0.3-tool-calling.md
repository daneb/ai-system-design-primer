# 0.3 Tool calling and structured output

![The application sends messages and tool definitions; the model returns a tool call with a name and JSON arguments; the application checks the schema and the user's permissions, runs the tool, and sends back the result, which is untrusted input; the loop repeats until the model gives a final answer.](../../images/0.3-tool-calling.svg)
<!-- source: images/src/0.3-tool-calling.mmd; render with scripts/diagrams.py -->

A model can only write tokens. Tool calling is a convention built on that. You describe some
functions in the request: a name, a description, and a schema for the arguments. When a function
would help, the model writes a structured request to call it and stops. Your code decides whether to
run it, runs it, and sends the result back in the next call.

The model never executes anything and never sees your code; it sees only the schema and the result.
Anthropic, OpenAI, Google, AWS and Microsoft all use this shape. They call it tool use or function
calling, and the field names differ. Every agent in Part 3 is this loop with more around it
([3.9](../3-components/3.9-workflows-and-agents.md)).

## Key terms

- **Tool definition:** the name, description and argument schema you send so the model knows a tool exists.
- **Tool call:** the model's structured request to run a tool, with an ID, the tool's name and JSON arguments.
- **Stop reason:** the field saying why the model stopped: finished, hit the output limit, or wants a tool run.
- **Structured output:** a reply constrained to match a JSON Schema, so your code can parse it reliably.
- **Agent loop:** your code calling the model, running the tools it asks for, and calling again until it finishes.

More in the [glossary](../5-appendix/5.6-glossary.md).

## How it works

### The loop

1. **Send** the messages and the tool definitions.
2. **The model replies** with one or more tool calls, and a stop reason saying it wants tools run.
3. **Your code checks** each call: does the tool exist, do the arguments match the schema, and may
   this user do this? Then it runs the tool.
4. **Send everything back**: the earlier messages, the model's reply, and a result for each call,
   matched by ID. Errors go back as results too, so the model can correct itself.
5. **Repeat** until the stop reason says the model has finished, or your step limit is reached.

- **You can steer the choice.** Let the model decide, require some tool call, force one named tool,
  or allow none.
- **Several calls can come at once.** Run independent calls in parallel and return all the results
  together.
- **Some tools run on the provider's side.** Built-in web search or code execution runs the same loop
  inside the provider. Software development kits can also run the loop for you; it is still there.

### Structured output

- **The same mechanism without an action.** Ask for a reply that matches a JSON Schema, such as a
  classification with a reason.
- **Strict modes constrain the tokens.** With them on, the provider only allows tokens that keep the
  output valid against the schema. Without them, matching is best effort, so parse defensively.
- **A valid shape isn't a correct answer.** The schema guarantees an amount is a number, not that it
  is the right number. Check business rules in code.

### What it costs

- **Definitions ride along on every call.** Each tool's name, description and schema are input tokens
  every time.
- **History grows with every step.** Each call and result joins the conversation, and the whole
  conversation is resent ([0.1](0.1-tokens-context-and-sampling.md)).
- That is why large tool sets need tool search ([3.10](../3-components/3.10-multi-agent-and-protocols.md)),
  old results get cleared ([3.3](../3-components/3.3-context-engineering.md)), and prefixes get cached
  ([3.13](../3-components/3.13-caching.md)).

### Where it goes wrong

- **Tool results are untrusted input.** A web page, email or document can carry instructions the model
  may follow (prompt injection, [2.4](../2-trade-offs/2.4-capability-vs-security.md)).
- **The model can pick the wrong tool or wrong arguments.** Validation catches bad shapes; only a
  permission check catches a well-formed call the user isn't allowed to make.

## Example

A bank's servicing assistant may only read balances. It has two tools defined, `get_balance` and
`transfer`, because the same definitions serve a back-office agent. In
[Lab 0.3](../../labs/0.3-tool-calling/README.md), a scripted model proposes 2,000 calls: 3% have
malformed arguments and 1% are transfers.

Running calls as proposed sent 60 malformed calls to the core system and executed 19 transfers.
Schema validation stopped the malformed calls but still ran all 19 transfers, because they were well
formed. Adding a permission check for the session stopped them too. The team removes `transfer` from
this assistant's definitions and keeps the permission check anyway.

The same lab shows the token bill. A 20-step task with 50 tool definitions used 291,060 input tokens,
against 102,060 with 5 tools.

## What it means for design

- Treat every tool call as a request from an untrusted client: validate, authorise, then run.
- Give each agent only the tools its job needs, with clear names and descriptions.
- Set a step limit and a token budget for every loop.
- Return errors to the model as results, with enough detail to fix the call.
- Use structured output wherever code, not a person, reads the reply.

## Disadvantages and pitfalls

- **Believing the model "ran" something.** It only asked; your code ran it, and your code is
  accountable.
- **Validation without authorisation.** A perfectly formed call can still be one the user may not make.
- **Trusting tool results.** Retrieved content can steer the next step.
- **Tool sprawl.** Every definition costs tokens on every call and makes the wrong choice more likely.

## Flashcards

Q: Does the model execute a tool?
A: No. It returns a structured request; your code decides whether to run it, runs it, and sends the result back.

Q: What does the model see of a tool?
A: Only its definition (name, description, argument schema) and the results you return; never your code.

Q: How does your code know the model wants a tool run?
A: The stop reason says so, and the reply contains one or more tool calls, each with an ID, a name and arguments.

Q: What does a strict structured-output mode guarantee, and what not?
A: That the output matches the schema; not that the values are correct.

Q: Why isn't schema validation enough before running a tool call?
A: A well-formed call can still be one the user isn't allowed to make; you also need a permission check.

Q: Why do agent loops get more expensive with each step?
A: Tool definitions and the growing history of calls and results are resent as input on every call.
