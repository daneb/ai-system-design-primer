# 2.2 Determinism vs autonomy

![Diagram for 2.2 Determinism vs autonomy: Plain code, One model call with retrieval, Workflow code decides the steps, Agent model decides the steps, Multi-agent](../../images/2.2-determinism-vs-autonomy.svg)
<!-- source: images/src/2.2-determinism-vs-autonomy.mmd; render with scripts/diagrams.py -->

Move right only when the option to the left demonstrably can't do the job.

Who decides what happens next: your code or the model? In a **workflow**, code fixes the steps and the
model fills them in. In an **agent**, the model chooses which tool to call, in a loop, until it decides
it is done ([3.9](../3-components/3.9-workflows-and-agents.md)). Autonomy buys flexibility for tasks
whose steps you can't predict. It costs predictability of the path, the cost, the latency and the
result.

Anthropic, OpenAI, Google, AWS and Microsoft give the same default: use the simplest thing that
works. Microsoft puts it bluntly: if you can write a function for the task, do that instead of using
an agent.

## Key terms

- **Workflow:** model calls joined by fixed code paths; the code decides what happens next.
- **Agent:** a model that chooses which tool to call next, in a loop, until it decides the task is done.
- **Tool:** a function the model can ask your code to run, such as "search orders" or "send email".
- **pass^k:** the chance a system succeeds on all k repeated tries of the same task; it measures consistency.
- **Step cap:** a hard limit on how many steps an agent may take before it must stop.

More in the [glossary](../5-appendix/5.6-glossary.md).

## What autonomy costs

- **Reliability compounds.** If every step must succeed, ten steps at 95% each succeed about 60% of
  the time. Workflows make it easy to check and retry between steps; agent loops don't.
- **Consistency drops with repetition.** On the τ-bench benchmark, one agent solved about 61% of
  tasks once. It solved only about 25% of them in all of eight tries (Yao et al., 2024). The customer who
  comes back eight times feels the second number.
- **Cost and latency get a long tail.** The model decides when to stop, so some requests take many
  more calls than the average.
- **Testing and audit get harder.** A workflow has paths you can enumerate. An agent's path is chosen
  at run time, so you test outcomes statistically and explain single runs from traces.
- **The attack surface grows.** Tool autonomy is what an injected instruction exploits
  ([2.4](2.4-capability-vs-security.md)).

## What autonomy buys

- Handling requests and documents the designer didn't foresee.
- Investigations where the next step depends on the last result.
- Recovering from an error by trying something else, which a fixed pipeline can't.
- Replacing a rule set nobody can maintain any more.

## Example

A bank wants to handle "where's my card?" requests. The steps are always the same: verify the
customer, look up the card order, check courier status, reply. As a **workflow**, that's four fixed
steps; at 99% each, it succeeds about 96% of the time, costs the same every time, and every failure
points to one step.

Built as an **agent** that decides for itself, the same task needs more model calls, and the path
varies. If each of its ten decisions is right 95% of the time, the run succeeds about 60% of the time.
The workflow wins here.

A fraud analyst's investigation is different: the next lookup depends on what the last one found. That
step is where an agent earns its place, inside a workflow that still owns intake, approval and the
case record.

## How to decide

1. **Can plain code do it?** Use code.
2. **Can one well-prompted call with retrieval do it?** Most question answering can.
3. **Are the steps known in advance?** Use a workflow: chaining, routing, parallel calls or an
   evaluator loop.
4. **Is only one step open-ended?** Put an agent *inside* a workflow. Code owns the process
   (intake, approvals, records); the agent gets the judgment step.
5. **Is one agent overloaded** with tools and responsibilities? Only then consider several
   ([3.10](../3-components/3.10-multi-agent-and-protocols.md)).

Whatever you choose, bound it: step caps, token budgets, allowed tools, and a human for irreversible
actions.

## Disadvantages and failure modes

- **Agent-first design** for a task with fixed steps, then fighting its unpredictability.
- **Measuring single-try success only**, and discovering the inconsistency in production.
- **No step cap or budget**, so one confused run loops for minutes and costs dollars.
- **Rigid workflows for open-ended work**, which push every exception to a person and save nothing.

## Flashcards

Q: What is the difference between a workflow and an agent?
A: In a workflow, code fixes the sequence of steps and the model fills them in. In an agent, the model decides which tool to call next, in a loop, until it decides it is done.

Q: What does Microsoft's Agent Framework say to do if you can write a function for the task?
A: Write the function instead of using an AI agent.

Q: Ten steps that each succeed 95% of the time, all required: end-to-end success?
A: About 60% (0.95^10), assuming independent steps and no recovery.

Q: What does pass^k measure, and why does it matter for customer-facing agents?
A: The chance of succeeding on the same task in all k tries. It exposes inconsistency that single-try success hides; on τ-bench a 61% agent fell to about 25% over eight tries.

Q: What hybrid fits when only one step needs judgment?
A: A deterministic workflow owns the process and calls an agent for the judgment step.
