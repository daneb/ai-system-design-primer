# 3.10 Multi-agent topologies and protocols (MCP, A2A)

![A user works with a host app or lead agent. It uses MCP to call tools and read resources on a CRM server and a documents server. It uses A2A to delegate a task to a remote agent run by another team or vendor. That remote agent uses MCP to reach its own payments server.](../../images/3.10-multi-agent-and-protocols.svg)
<!-- source: images/src/3.10-multi-agent-and-protocols.mmd; render with scripts/diagrams.py -->

Once a system has several agents and many tools, two questions come up. **Topology:** who talks to
whom? **Protocol:** in what format, with what security? Two open protocols now cover most of this.
**MCP** (Model Context Protocol) connects an agent to tools and data. **A2A** (Agent2Agent) connects
an agent to another agent. Both are now governed by the Linux Foundation's Agentic AI Foundation.

## Key terms

- **MCP (Model Context Protocol):** an open protocol for connecting an AI app to tools, data and prompts exposed by servers.
- **A2A (Agent2Agent):** an open protocol for one agent to discover another and delegate a task to it, without seeing its internals.
- **Agent card:** an A2A agent's public description of its skills, endpoints and security, at a well-known URL.
- **Topology:** who talks to whom: orchestrator, handoff, hierarchy, peer-to-peer or group chat.
- **Tool poisoning:** hidden instructions in a tool's description, which the model reads and may follow.

More in the [glossary](../5-appendix/5.6-glossary.md).

## Topologies

- **Orchestrator (supervisor).** A lead agent hands out work and checks results. The default; it
  contains errors best ([2.5](../2-trade-offs/2.5-single-vs-multi-agent.md)).
- **Handoff.** A triage agent passes the conversation to a specialist, which takes over ([3.9](3.9-workflows-and-agents.md)).
- **Hierarchical.** Orchestrators of orchestrators, for large problems. Each level adds hand-off loss.
- **Peer-to-peer (decentralised).** Agents message each other with no lead. Flexible, hard to debug.
- **Group chat or blackboard.** Agents share one conversation or workspace, with a manager picking
  who speaks next.

## Protocols

- **MCP: agent to tool.** A *host* (the agent app) runs MCP *clients* that connect to MCP *servers*.
  A server exposes *tools* (actions), *resources* (data) and *prompts* (templates). Runs locally over
  stdio or remotely over HTTP. Turns M apps × N systems into M + N integrations. The July 2026 version
  made the protocol stateless: every request carries its version, so servers can scale behind a load
  balancer.
- **A2A: agent to agent.** An agent publishes an *agent card* (a JSON file at a well-known URL) listing
  its skills, endpoints and security. Another agent sends it a *task* and gets *messages* and
  *artifacts* back, including for long-running work. Agents stay opaque: the caller never sees the other
  agent's prompts, memory or tools. Version 1.0 shipped in 2026 with signed agent cards.
- **They complement each other.** An agent reached over A2A typically uses MCP for its own tools.

## Security essentials

- **Every MCP server and A2A agent is a third party in your agent's context.** Tool descriptions and
  agent cards can carry injected instructions ([3.17](3.17-security.md)).
- **Remote MCP uses OAuth 2.1.** Tokens are bound to one server; a server must not pass a client's
  token on to another API (*token passthrough* is forbidden).
- **Local MCP servers run with the user's privileges.** Sandbox them.
- **Put a gateway and a registry in front.** Approve servers and agents, enforce authentication and
  rate limits, and log every call ([3.1](3.1-ai-gateway-and-router.md)).

## Example

Ten internal assistants each need the same 20 systems (CRM, document store, ticketing, and so on).
Built point-to-point, that's 200 integrations, each with its own authentication. With MCP, each system
gets one MCP server and each assistant one MCP client: 30 pieces ([Lab 3.10](../../labs/3.10-multi-agent-and-protocols/README.md)).

The catch arrives at 58 tools: their definitions take about 55,000 tokens on every call. With prompt
caching that list is cheap, and in the lab loading everything stayed cheaper than searching for tools
until about 90 tools. Past that, the team switches to loading tools on demand. Every MCP server sits behind the gateway with
an approved registry, so a changed tool description is caught before an agent reads it.

## When to use

- **MCP:** whenever agents need the same tools or data across apps, teams or vendors.
- **A2A:** when agents are owned by different teams or vendors and must cooperate without sharing
  internals.
- **Neither:** one agent with a few in-process tools. Plain function calls are simpler.

## Disadvantages

- **Tool definitions cost tokens on every call.** Fifty-odd tools can take 55k tokens. Load on
  demand or split across sub-agents ([3.3](3.3-context-engineering.md)).
- **Young, fast-moving specs.** MCP has shipped five revisions since late 2024, one of them breaking.
- **Wider attack surface** and more identities to govern.

## Flashcards

Q: MCP vs A2A in one line each?
A: MCP connects an agent to tools and data; A2A connects an agent to another agent, which stays opaque.

Q: What three things can an MCP server expose?
A: Tools (actions), resources (data) and prompts (templates).

Q: What is an A2A agent card?
A: A JSON document at a well-known URL describing an agent's skills, endpoints and security requirements, used for discovery.

Q: How does a shared protocol change integration count?
A: From M apps × N systems point-to-point connectors to M clients + N servers.

Q: What is token passthrough, and why is it forbidden in MCP?
A: A server forwarding a client's token to another API without checking it was issued to the server; it bypasses controls and breaks audit (a confused-deputy risk).

Q: Which topology contains errors best?
A: An orchestrator that checks sub-agents' results before using them.
