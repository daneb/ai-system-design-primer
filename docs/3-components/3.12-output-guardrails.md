# 3.12 Output guardrails and validation

![Model output passes four checks in order: shape (does it parse and match the schema), grounding (is it supported by the sources), policy, and safe handling, before it reaches the user or a downstream system. A failure at any of the first three leads to a retry, a fallback, a refusal or an escalation.](../../images/3.12-output-guardrails.svg)
<!-- source: images/src/3.12-output-guardrails.mmd; render with scripts/diagrams.py -->

Output guardrails check what a model produced before anyone or anything uses it. Input guardrails
([3.2](3.2-input-guardrails.md)) decide what the model sees; output guardrails decide what leaves.

## Key terms

- **Output guardrail:** a check on what a model produced before anyone or anything uses it.
- **JSON Schema:** a description of the fields, types and allowed values a JSON document must have.
- **Grounding:** each claim in an answer follows from the sources it cites.
- **Quote check:** confirming in code that a quoted passage appears in the cited source.
- **Improper output handling:** using model output unsafely downstream, such as in a browser, SQL query or shell (OWASP LLM05).

More in the [glossary](../5-appendix/5.6-glossary.md).

## The four checks

- **Shape.** Is it valid JSON matching the schema, with allowed values? Providers now offer
  *structured outputs*: you pass a JSON Schema and generation is constrained so only matching output
  can be produced. That guarantees the shape, not the content: a schema ensures `amount` is a number,
  not that it's the right number. Validate business rules in code.
- **Grounding.** For answers built on sources ([3.4](3.4-retrieval-pipeline.md)), does each claim follow
  from what it cites? Three layers, cheapest first:
  - ask the model to quote its sources and to say "I don't know";
  - check in code that each quoted passage really exists in the cited source;
  - check meaning with a grounding service or an LLM judge ([3.15](3.15-evals.md)).
- **Policy.** Harmful content, personal data, and things only output can reveal: system-prompt
  fragments, secrets, internal identifiers, unwanted links.
- **Safe handling.** Treat the model like an untrusted user. Output rendered in a browser, used in SQL
  or passed to a shell is how old web vulnerabilities return (OWASP LLM05). Encode for the context,
  parameterise queries, never execute output directly.

On failure: retry with the error (for shape), fall back to a safe answer, say "I don't have enough
information", or route to a person. Log every failure; failures are your next eval cases.

## Example

An assistant answers policy questions and returns JSON: `answer`, `quote`, `source_id`. Structured
outputs guarantee the shape. A code check confirms `quote` appears word for word in the document
`source_id` points to: free, instant, and it catches invented quotes.

In [Lab 3.12](../../labs/3.12-output-guardrails/README.md), the quote check caught every fabricated
quote but missed answers that quoted the source correctly and then claimed something it doesn't say,
including the opposite. So for answers that customers act on, a grounding check runs after the cheap check: a model compares
the claim with the quote. The answer is rendered as plain text, never as HTML.

## When to use

- Structured outputs whenever code consumes the output.
- Grounding checks on answers that cite sources, especially customer-facing or regulated ones.
- Encoding and validation wherever output reaches a browser, database, shell or API.

## When to avoid

- Parsing free text with regular expressions when schema-enforced output is available.
- Treating a passed grounding check as proof the answer is right. If retrieval returned an outdated
  policy, a perfectly grounded answer is still wrong.

## Disadvantages

- **Quote checks miss misused quotes.** A claim can cite a real sentence and still say something it
  doesn't support, even the opposite.
- **Semantic checks cost a call** and add latency; run cheap deterministic checks always and expensive
  ones by risk.
- **Streaming and checking conflict.** Text reaches the user before a full-response check runs. Buffer,
  check per chunk, or hold back anything that triggers actions.
- **Strict grounding produces more "I don't know"** answers, which users may find unhelpful.

## Flashcards

Q: What do structured outputs guarantee, and what don't they?
A: They guarantee the output matches the JSON Schema (shape and types). They don't guarantee the values are correct; validate business rules in code.

Q: What are three layers of grounding check, cheapest first?
A: Prompt for quotes and "I don't know"; verify cited quotes exist in the cited source in code; check meaning with a grounding service or LLM judge.

Q: What can a deterministic quote check not catch?
A: A claim that cites a real quote but says something the quote doesn't support, or contradicts it.

Q: What is OWASP LLM05, and the core mitigation?
A: Improper Output Handling: model output causing XSS, SQL injection or code execution downstream. Treat the model as an untrusted user: validate, encode for context, parameterise, never execute directly.

Q: Why is streaming a problem for output guardrails?
A: Text reaches the user before a full-response check can run; buffer, check per chunk, or hold back high-risk content.
