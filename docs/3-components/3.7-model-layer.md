# 3.7 Model layer: selection, structured outputs, streaming

![Diagram for 3.7 Model layer: selection, structured outputs, streaming: Task and quality bar, Eval on candidate models, Pick: best that meets the bar, then cheapest that still does, Pin a version, Call: structured output, tools, streaming](../../images/3.7-model-layer.svg)
<!-- source: images/src/3.7-model-layer.mmd; render with scripts/diagrams.py -->

The model layer is the part of the system that calls a model: which one, which version, with what
settings, and in what output shape. The model is your most important dependency and the one that
changes most often, so treat it like a dependency you upgrade deliberately, not a constant.

## Key terms

- **Model tier:** the size class a provider sells (large, medium, small); larger is usually better, slower and dearer.
- **Pinned version:** a fixed model snapshot that won't change underneath you, as opposed to an alias that moves to the latest version.
- **Structured outputs:** passing a JSON Schema so the provider constrains the model to produce only matching output.
- **Tool calling:** the model returns a request to run a function you described; your code decides whether to run it.
- **Streaming:** sending tokens to the user as they're generated, so the first words appear sooner.
- **Model retirement:** the date after which a model version stops being served.

More in the [glossary](../5-appendix/5.6-glossary.md).

## Choosing a model

- **Accuracy first, then cost and latency.** Reach your quality bar with the most capable model. Then
  try cheaper and faster ones, and keep the cheapest that still meets the bar. OpenAI states this rule
  directly; it matches the order in [2.1](../2-trade-offs/2.1-cost-quality-latency.md).
- **Tiers.** Every provider sells large, medium and small models, often with a dial for how long the
  model reasons before answering. Bigger and longer-thinking means better on hard tasks, slower and
  dearer.
- **Context window is a ceiling, not a target.** Accuracy falls as input grows, well before the window
  is full. Facts in the middle of a long input are used worst. Send the least context that
  answers the question ([3.4](3.4-retrieval-pipeline.md)).
- **Choose on your eval, not a leaderboard.** Public benchmarks don't measure your task
  ([3.15](3.15-evals.md)).

## Calling it

- **Structured outputs.** Pass a JSON Schema and the provider constrains the output to it. Use it
  whenever code reads the result ([0.3](../0-orientation/0.3-tool-calling.md), [3.12](3.12-output-guardrails.md)).
- **Tool calling.** The model returns a request to call a function you described; your code decides
  whether to run it ([2.4](../2-trade-offs/2.4-capability-vs-security.md)).
- **Streaming.** Send tokens as they're generated. It improves perceived latency, not total time or
  cost, and makes output checks harder.
- **Limits.** Set a maximum output length and a timeout on every call.

## Versions and lifecycle

- **Pin a specific version in production.** Aliases that move to the latest version are convenient
  for experiments and can change behaviour without a code change.
- **Every model retires.** Providers publish lifecycle stages and dates; some cloud deployments
  upgrade automatically at retirement unless you set them not to, and some simply stop working.
- **Treat an upgrade like a dependency upgrade:** re-run the eval, compare quality, latency, cost and
  token counts (new models can tokenise differently), then roll out gradually with rollback.

## Example

A team has three candidate models for classifying complaints, and a 100-case eval with a 90% target.
The cheapest model scores 91%. It looks like a win, but with 100 cases a score is only known to within
about ±8 points. In [Lab 3.7](../../labs/3.7-model-layer/README.md), "pick the cheapest that passes" on
100 cases chose a model that was really below target 41% of the time.

The team grows the eval to 1,000 cases and the cheap model scores 88%, so they pick the middle tier,
which scores 92%. They pin its version and set a 20-second timeout and a 300-token output limit. The provider's
retirement date for that version goes in their calendar, with the re-eval it will need.

## When to use a larger model

- The cheaper model misses the quality bar on your eval, with a margin you trust.
- Hard reasoning, long multi-step tasks, or high cost of a wrong answer.

## When to use a smaller model

- High-volume, narrow tasks (classification, extraction, routing) where it meets the bar.
- Steps inside a workflow where the large model's quality isn't needed ([2.1](../2-trade-offs/2.1-cost-quality-latency.md)).

## Disadvantages and failure modes

- **Choosing on a small eval.** With 100 cases, picking the cheapest model that scored above target
  often picks one that's really below it.
- **Floating aliases in production**, so behaviour changes overnight.
- **No owner for retirement dates**, so a model disappears mid-quarter.
- **Stuffing the context window** because it's there.
- **One model for everything**, at the price of the hardest task.

## Flashcards

Q: What order does OpenAI recommend for model selection?
A: Optimise for accuracy first until you hit the target, then keep that accuracy with the cheapest, fastest model possible.

Q: Why pin a model version in production?
A: A moving alias can change behaviour without a code change; pinning makes upgrades explicit, tested changes.

Q: Why is a large context window not a reason to fill it?
A: Accuracy falls as input grows, and facts in the middle are used worst, well before the window is full.

Q: What can go wrong when you pick the cheapest model whose eval score meets the target?
A: With a small eval, a cheaper model can score above its true accuracy by luck; you ship a model that's really below target.

Q: What should a model upgrade go through?
A: The same eval as the current model, comparison of quality, latency, cost and token counts, then a gradual rollout with rollback.
