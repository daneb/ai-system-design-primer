# 3.8 Serving internals

![Diagram for 3.8 Serving internals: Requests, Scheduler continuous batching, Prefill whole prompt at once, KV cache paged blocks, Decode one token per step, Streamed tokens](../../images/3.8-serving-internals.svg)
<!-- source: images/src/3.8-serving-internals.mmd; render with scripts/diagrams.py -->

Serving internals are what happens between a request arriving and tokens streaming back. You need
them if you host open-weight models yourself, and they explain the prices, limits and latency you see
from hosted APIs too.

A model answers in two phases. **Prefill** reads the whole prompt in one parallel pass and produces
the first token. **Decode** then produces one token per step, each step reading every model weight
from memory. Prefill keeps the arithmetic units busy; decode waits on memory. Almost every serving
technique exists to keep the hardware busy in decode without making users wait.

## Key terms

- **Prefill and decode:** reading the whole prompt in one pass, then writing the answer one token at a time.
- **KV cache:** stored attention keys and values for tokens already processed, so they aren't recomputed; it grows with every token and request.
- **Continuous batching:** re-forming the batch at every step, so finished requests leave and waiting ones join.
- **Prefix caching:** reusing the KV cache for a prompt beginning that many requests share.
- **Speculative decoding:** a small model drafts several tokens and the large model checks them in one pass.
- **Quantization:** storing weights or cache in fewer bits, so there is less memory to read and more room for requests.

More in the [glossary](../5-appendix/5.6-glossary.md).

## The building blocks

Prefill, decode and the KV cache are introduced in [0.2](../0-orientation/0.2-inside-a-model-call.md); this page goes further.

- **KV cache.** The attention keys and values for every token already processed, kept so they aren't
  recomputed each step. It grows with every token and every concurrent request, and usually decides
  how many requests fit at once.
- **Continuous batching.** The scheduler re-forms the batch at every step: finished requests leave,
  waiting ones join. Every modern engine does this ([2.7](../2-trade-offs/2.7-throughput-vs-latency.md)).
- **Paged KV cache.** Store the cache in small fixed blocks, like operating-system pages, instead of
  one reserved slab per request. The paper that introduced this (PagedAttention) cut wasted cache memory
  from 60–80% to under 4%.
- **Prefix caching.** Reuse the cache for a prompt prefix that many requests share, such as a system
  prompt, so it isn't prefilled again ([3.13](3.13-caching.md)).
- **Chunked prefill.** Split a long prompt into chunks interleaved with other requests' decode steps,
  so one huge prompt doesn't stall everyone.
- **Disaggregation.** Run prefill and decode on separate accelerators so they stop interfering, and
  move the cache between them. Used at large scale.
- **Speculative decoding.** A small draft model guesses several tokens; the large model checks them all
  in one pass. Output is identical to the large model's; speed rises 2–3× when guesses are usually right.
- **Quantization.** Store weights (and sometimes the cache) in fewer bits. Less memory to read means
  faster decode and more room for requests.
- **Parallelism.** Split a model too big for one accelerator across several, by layer slices
  (tensor parallel) or layer groups (pipeline parallel).

## Example

A team self-hosts an 8-billion-parameter model on one 80 GB accelerator for a document assistant with
128,000-token prompts. The weights take 16 GB. One full-length request needs about 69 GB of KV cache
without grouped-query attention, so only one fits, and barely.

With grouped-query attention (built into many current models) the same request needs 17 GB; storing
the cache in 8 bits halves that to 8.6 GB ([Lab 3.8](../../labs/3.8-serving-internals/README.md)). Now
about seven long requests fit at once. Prefix caching lets requests that share the same documents skip
re-reading them, and chunked prefill keeps one 128k prompt from stalling everyone else's answers.

## When to use

- **You host models yourself:** use an established open-source serving engine rather than writing
  serving code. The techniques above come built in; your job is configuration and capacity.
- **Long prompts with shared prefixes** (RAG, agents): turn on prefix caching and route requests with
  the same prefix to the same replica.
- **Latency-sensitive, low-concurrency work:** speculative decoding.

## When to avoid

- Building your own engine. The field moves monthly.
- Speculative decoding on a saturated server or with a poorly matched draft model: it can be slower.
- Aggressive quantization without evaluating your own task.

## Disadvantages

- **Configuration is subtle.** Batch limits, chunk sizes and cache settings trade latency against
  throughput; defaults change between versions.
- **Long context is expensive in memory.** One 128k-token request can need more cache than the model's
  own weights.
- **Quantization isn't free everywhere.** 8-bit floating point was effectively lossless in a large 2024
  study; 4-bit lost a little; your task may differ.
- **More moving parts at scale.** Disaggregation and cache-aware routing add components to run.

## Flashcards

Q: What are the two phases of generating a response, and what limits each?
A: Prefill (process the whole prompt in parallel; limited by compute) and decode (one token per step; limited by memory bandwidth).

Q: What is the KV cache, and why does it limit concurrency?
A: The stored attention keys and values for every processed token. It grows with each token and each concurrent request, so memory for it caps how many requests fit.

Q: What problem does a paged KV cache solve?
A: Fragmentation and over-reservation: storing the cache in small blocks cut wasted cache memory from 60–80% to under 4% in the PagedAttention paper.

Q: Why is speculative decoding lossless?
A: The large model verifies every drafted token and a rejection-sampling rule ensures the output distribution is exactly the large model's.

Q: What does chunked prefill fix?
A: A long prompt's prefill stalling every other request's decode; splitting it into chunks keeps per-token latency smooth.
