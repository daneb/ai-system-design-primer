# 3.9 Workflows and agents

![Two panels. Workflows, where code decides the path: prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimizer. Agent, where the model decides the path: goal, the model chooses a tool, the tool result gives ground truth, then a check for done or budget spent loops back.](../../images/3.9-workflows-and-agents.svg)
<!-- source: images/src/3.9-workflows-and-agents.mmd; render with scripts/diagrams.py -->

This hub covers how model calls are put together. The building block is an *augmented model*: one
call with access to retrieval, tools and memory. Systems combine these blocks in two ways. In a
**workflow**, your code sets the path; in an **agent**, the model chooses the next step in a loop. Which
to use is the trade-off in [2.2](../2-trade-offs/2.2-determinism-vs-autonomy.md): start with the
simplest thing that works.

Anthropic, OpenAI, Google, AWS and Microsoft describe the same small set of patterns under different
names.

## Key terms

- **Augmented model:** one model call with access to retrieval, tools and memory; the building block of every pattern.
- **Prompt chaining:** a fixed sequence of calls, each working on the last one's output, with checks in code between.
- **Routing:** classifying an input and sending it to a specialised prompt or model.
- **Orchestrator-workers:** a model splits a task into subtasks at run time, hands them out, and combines the results.
- **Evaluator-optimizer:** one call drafts, another checks against clear criteria and sends it back for revision.
- **Stopping condition:** what ends an agent loop: goal reached, step cap, budget, timeout, or a human checkpoint.

More in the [glossary](../5-appendix/5.6-glossary.md).

## Workflow patterns

- **Prompt chaining.** A fixed sequence of calls, each working on the last one's output, with checks in
  code between steps. *Example:* draft a letter, check it against policy, then translate it.
- **Routing.** Classify the input, then send it to a specialised prompt or model. Lets you tune each path
  separately and send easy requests to cheaper models ([2.1](../2-trade-offs/2.1-cost-quality-latency.md)).
- **Parallelisation.** *Sectioning:* split independent subtasks and run them at once. *Voting:* run the
  same task several times and combine the answers for confidence.
- **Orchestrator-workers.** A model breaks the task into subtasks it decides at run time, hands them to
  workers, then combines the results. Unlike parallelisation, the subtasks aren't fixed in advance.
- **Evaluator-optimizer.** One call drafts, another checks against clear criteria and sends it back
  with feedback, until it passes or a round limit is hit.

## Agents

An agent is a model running in a loop: it reads the goal, chooses a tool, sees the result, and decides
whether it's done. Each step is a tool call ([0.3](../0-orientation/0.3-tool-calling.md)). The research name for the reason-then-act loop is *ReAct*. What makes it work:

- **Ground truth at every step.** Tool results, test output and data are how the agent knows whether
  it's making progress, rather than its own opinion.
- **Good tools.** Clear names, descriptions and parameters matter as much as the prompt. Fewer,
  well-defined tools beat many overlapping ones.
- **Stopping conditions.** A goal check, a step cap, a token budget, a timeout, and a human checkpoint
  for irreversible actions.

When one agent isn't enough, two shapes recur ([3.10](3.10-multi-agent-and-protocols.md)):

- **Manager (agents as tools).** A central agent calls specialists as tools and keeps ownership of the
  answer.
- **Handoff.** A triage agent passes the conversation to a specialist, which owns it from then on.

## Example

A team builds a quarterly-letter drafter. It's a **chain**: extract figures from the report, draft the
letter, check it against the style and compliance rules, translate. Code checks the figures match the
report between steps.

They add an **evaluator-optimizer** loop at the compliance check: a second call reviews the draft
against a checklist and sends it back with comments, up to three rounds. In
[Lab 3.9](../../labs/3.9-workflows-and-agents/README.md), a loop with an exact check lifted accuracy from
60% to 98%; with a weak judge that waved 40% of bad drafts through, only to 78%; beyond three rounds,
almost nothing more. So the team makes the compliance check mostly code (required phrases, banned
claims) and uses a model judge only for tone.

## When to use which

- **Steps known in advance:** chain, route or parallelise.
- **Subtasks only known at run time:** orchestrator-workers.
- **Quality checkable by clear criteria:** evaluator-optimizer.
- **Open-ended task, path unpredictable, results checkable:** an agent, inside guardrails and budgets.
- **Patterns compose.** A router can choose between chains; an agent can sit inside one workflow step.

## When to avoid

- An agent for a task with fixed steps ([2.2](../2-trade-offs/2.2-determinism-vs-autonomy.md)).
- An evaluator loop without a reliable evaluator.
- A framework you don't understand. Several providers advise starting with direct API calls; much of
  this is a few lines of code.

## Disadvantages

- **Every extra call adds latency and cost.** Chains add round trips; agents add many.
- **Loops need limits.** Without them, a confused agent repeats itself and burns budget.
- **An evaluator is the ceiling.** A weak judge waves bad drafts through; looping on it adds cost, not
  quality.
- **Errors compound** across steps unless checked between them.
- **Agents act through tools**, which is where security risk lives ([2.4](../2-trade-offs/2.4-capability-vs-security.md)).

## Flashcards

Q: Name Anthropic's five workflow patterns.
A: Prompt chaining, routing, parallelisation (sectioning or voting), orchestrator-workers, evaluator-optimizer.

Q: How does orchestrator-workers differ from parallelisation?
A: In parallelisation the subtasks are fixed in advance; in orchestrator-workers a model decides them at run time from the input.

Q: What gives an agent "ground truth" about its progress?
A: Results from the environment at each step: tool outputs, test results, data, rather than its own judgement.

Q: What stopping conditions should every agent have?
A: A goal check, a step cap, a token or cost budget, a timeout, and human approval for irreversible actions.

Q: Manager pattern vs handoff?
A: In the manager pattern a central agent calls specialists as tools and owns the answer; in a handoff the specialist takes over the conversation and owns it.

Q: What limits the benefit of an evaluator-optimizer loop?
A: The evaluator's accuracy. A weak evaluator accepts bad drafts, so extra rounds add cost without quality.
