## The trade-off

Every tool you give a model makes it more useful and gives an attacker more to work with. The root
cause is prompt injection: a model cannot reliably tell your instructions from instructions hidden in
the data it reads ([3.2](../3-components/3.2-input-guardrails.md)). No detector fixes this. When
researchers from OpenAI, Anthropic and Google DeepMind attacked 12 published defences with adaptive
attacks, most failed more than 90% of the time, against near-zero rates in their original papers
([Nasr et al., 2025](https://arxiv.org/abs/2510.09023)).

So the question is not "how do I stop injection?" but "what can an injected agent do?" You answer it
with architecture, and you pay for the answer in capability.

## Count to three

Simon Willison named the dangerous combination the
[lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/): access to private
data, exposure to untrusted content, and a way to communicate externally. With all three, an
attacker's text can make the agent read your data and send it out. Meta generalised it as the
[Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/) (October 2025): until injection can be reliably detected, an agent session
should have at most two of:

- **[A]** processing untrustworthy inputs,
- **[B]** access to sensitive systems or private data,
- **[C]** changing state or communicating externally.

Adding "changing state" widens the trifecta from data theft to unwanted actions: payments, deletions,
tickets ([Willison](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)).
If a session needs all three, it should not run autonomously; a human approves the C step. Meta is
clear that the rule supplements least privilege and other controls rather than replacing them.

The rule is easy to apply and easy to get wrong, because the hard part is classifying tools:

- Retrieved documents, uploaded files, emails, web pages and other agents' outputs are all [A].
- A Markdown renderer that loads images, a `fetch_url` tool, or a link the user may click are all [C]:
  each can carry data out in a URL. After a Markdown-image exfiltration report, Microsoft blocked that
  technique deterministically, along with generating certain untrusted links ([MSRC](https://www.microsoft.com/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)).
- "Session" is the unit. Splitting work into separate sessions that pass only structured data is the
  usual fix.

[Lab 2.4](../../labs/2.4-capability-vs-security/README.md) audits seven example agents. Three break
the rule, one of them a "read-only" support chat that renders Markdown. With a detector that misses
only 1% of attacks, 100,000 sessions a day still yields about 20 compromised sessions.

## Patterns that buy back capability

Beurer-Kellner et al. (14 authors including IBM, Google, Microsoft and ETH Zurich) describe six
patterns that trade generality for provable limits on what injected text can do
([paper](https://arxiv.org/abs/2506.08837); [summary](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)):

| Pattern | Idea | What it gives up |
|---|---|---|
| Action-selector | The model picks from a fixed list of actions and never sees their results | Almost all flexibility |
| Plan-then-execute | Fix the tool calls before reading untrusted data | Injected data can still shape arguments, not which tools run |
| Map-reduce | Isolated sub-agents each process one untrusted item; results are combined by code or a constrained model | Cross-document reasoning |
| Dual LLM | A privileged model plans and calls tools; a quarantined model reads untrusted text, has no tools, and returns references | Complexity; the privileged model can't read the content |
| Code-then-execute | The privileged model writes a program; an interpreter tracks where each value came from and enforces policies (CaMeL) | Engineering effort; some tasks fail |
| Context-minimisation | Drop the user's prompt from context once it has been turned into a query | Conversational follow-ups |

CaMeL, from Google DeepMind, is the most complete: it tags values with their source and blocks, for
example, sending a document to an address that came from untrusted text
([Debenedetti et al., 2025](https://arxiv.org/abs/2503.18813)). Its authors are explicit that it does
not stop text-only manipulation such as a misleading summary or a phishing link shown to the user.

## Where the providers converge

All five say the same thing in different words: limit what the agent can do, enforce it outside the
model, and keep a human on the irreversible steps.

- **Google** lists three principles for agents: well-defined human controllers, carefully limited
  powers, and observable actions and planning, with deterministic controls alongside reasoning-based
  defences ([Google](https://research.google/pubs/an-introduction-to-googles-approach-for-secure-ai-agents/)).
- **Microsoft** treats indirect injection as an inherent risk and layers probabilistic defences
  (Spotlighting, Prompt Shields) with deterministic ones (data governance, user consent, blocked
  exfiltration paths) ([MSRC](https://www.microsoft.com/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)).
- **OpenAI** rates each tool low, medium or high risk (read or write, reversible or not, permissions,
  financial impact) and sends high-risk actions to a human
  ([practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)).
- **Anthropic** sandboxes Claude Code with both filesystem and network isolation, noting that either
  alone leaves an escape route; in its internal use this cut permission prompts by 84%
  ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)).
- **AWS** puts Cedar policies on the AgentCore Gateway, evaluating every tool call and its arguments
  deterministically, outside the agent's code ([AWS](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-getting-started.html)).
- **OWASP** names the failure Excessive Agency, caused by excessive functionality, permissions or
  autonomy, and says authorisation belongs in downstream systems, not in the model
  ([LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)).

Anthropic's sandboxing result is the useful surprise: tighter boundaries gave *more* autonomy, because
safe actions no longer needed approval. Security and capability trade off per session, not overall.

## How to decide

1. List every tool and mark it A, B or C. Be pessimistic about A and C.
2. For each session, count. Three means redesign: split the session, drop a tool, or gate C behind
   human approval.
3. Narrow each tool: read-only scopes, the user's own identity (OAuth on-behalf-of), allow-listed
   recipients and hosts, amount limits.
4. Enforce those limits in code or a policy engine, never in the prompt.
5. Keep detectors as a layer that reduces frequency, and monitor what gets through.

## Failure modes

- **Trusting a detector as the boundary.** It lowers the rate; adaptive attackers raise it again.
- **Calling retrieval "trusted".** Internal documents written by customers, vendors or anyone with
  edit rights are untrusted input.
- **Forgetting covert outbound channels**: image URLs, link previews, DNS, logs sent to third parties.
- **Approval fatigue.** Prompting for every action trains people to click yes. Approve few, high-impact
  actions, and sandbox the rest.
- **One shared service identity** for all users, so an injected agent can reach everyone's data.
