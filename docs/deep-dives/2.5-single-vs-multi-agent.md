# 2.5 Single-agent vs multi-agent: deep dive

## What providers say

| Provider | Guidance | Source |
|---|---|---|
| Anthropic | Multi-agent (orchestrator-worker) suits open-ended, breadth-first research where steps can't be predicted and work runs in parallel; less suited to tasks where agents must share context or have many dependencies, such as most coding. Burns tokens fast. | [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) |
| OpenAI | Maximise a single agent first; split when prompts have too much conditional logic or tools overlap or overload. Two multi-agent shapes: manager (agents as tools) and decentralised handoffs. | [Practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) |
| Microsoft | Default to a single agent; start multi-agent only for security or compliance boundaries, multiple owning teams, or planned growth. Distinct roles don't by themselves justify it; coordination overhead can cancel concurrency gains. Move to multi-agent only when testing shows limits you can't fix in one agent. | [Cloud Adoption Framework](https://learn.microsoft.com/azure/cloud-adoption-framework/ai-agents/single-agent-multiple-agents) |
| Google | Single-agent first; multi-agent patterns (sequential, parallel, coordinator, hierarchical) for complex work. Research: coordination helps parallelisable tasks and hurts sequential ones. | [Design patterns](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system); [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/) |
| AWS | Multi-agent collaboration (supervisor and collaborators) in Bedrock Agents and Strands; prescriptive guidance frames it as an event-driven pattern. | [AWS agentic patterns](https://docs.aws.amazon.com/prescriptive-guidance/latest/agentic-ai-patterns/introduction.html) |

## The research

- **Anthropic (2025).** Lead Claude Opus 4 with Claude Sonnet 4 sub-agents beat single-agent Opus 4 by
  90.2% on an internal research eval. On BrowseComp, token usage explained 80% of performance variance;
  tool-call count and model choice explained most of the rest (95% together). Agents use about 4× the
  tokens of chat, multi-agent about 15×. A model upgrade gave more than doubling the token budget.
- **Google Research, Google DeepMind and MIT (Kim et al., Dec 2025; v3 Apr 2026).** 260 configurations
  across six benchmarks (an earlier version reported 180), five
  architectures (single; independent, centralised, decentralised, hybrid multi-agent), three model
  families. Coordination gave +80.8% on a parallelisable finance task and −39% to −70% on sequential
  planning; every multi-agent variant degraded sequential reasoning. Independent agents amplified errors
  17.2×, centralised 4.4×. Returns turned negative once single-agent accuracy passed about 45%. Tool-heavy
  tasks suffered most from coordination overhead. A model using measured coordination properties
  predicted the best architecture for 87% of held-out configurations.
- **Cemri et al. (UC Berkeley, NeurIPS 2025).** 1,642 traces from seven frameworks; 14 failure modes in
  three groups (system design, inter-agent misalignment, task verification); failure rates of 41–86.7%
  across systems. System design issues were the largest group (44.2%), then inter-agent misalignment (32.3%) and task
  verification (23.5%), summing the paper's per-mode shares. Fixes needed
  structural redesign, not prompt tweaks.
- **Cognition (2025, 2026).** "Don't build multi-agents": share full context and avoid conflicting
  implicit decisions; parallel writers produce inconsistent work. The April 2026 follow-up reports a
  narrower class that works: agents contribute intelligence (review, search) while writes stay
  single-threaded; a reviewer with a clean context works best.

## Where they agree

- Start with one agent; measure before splitting.
- Parallel, independent, read-heavy work is where multi-agent pays.
- Keep decisions and writes in one place; use sub-agents for exploration and review.
- An orchestrator that checks results beats unchecked parallel agents.

## Where they differ

- **How far to go.** Anthropic ships a multi-agent product; Cognition argues for a narrow class only.
- **Organisational reasons.** Microsoft alone lists team ownership and compliance boundaries as reasons
  to start multi-agent, a governance view rather than a performance one.

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Agents act beyond their remit | OWASP LLM06; ASI03 (identity and privilege abuse) | One identity per agent; least-privilege tools; writes through one agent | Agent inventory with identities and permissions |
| Errors cascade between agents | ASI08 (cascading failures) | Central orchestrator that validates results; contracts for hand-offs | Validation logs; failure taxonomy over traces |
| Untrusted output passed as trusted instruction | OWASP LLM01; ASI07 (insecure inter-agent communication) | Treat agent messages as data; authenticate agents ([3.10](../3-components/3.10-multi-agent-and-protocols.md)) | Protocol configuration; message logs |
| Cost overrun | OWASP LLM10 | Budgets per run and per agent; caps on sub-agent count | Cost per task by design |
| No clear accountability | Model risk; audit | Named owner per agent; trace across agents ([3.16](../3-components/3.16-observability.md)) | Ownership register; end-to-end traces |
