# 2.7 Throughput vs per-request latency in serving: deep dive

Reference material for [2.7 Throughput vs per-request latency](../2-trade-offs/2.7-throughput-vs-latency.md).
Read that first.

## Where the sources agree

**Decode is memory-bound; batching amortises it.** Anyscale's 2023 analysis states that LLM inference
is memory-IO bound rather than compute bound, so throughput is largely set by how large a batch fits
in accelerator memory
([Anyscale](https://anyscale.com/blog/continuous-batching-llm-inference)). Together AI gives the
small-batch upper bound: tokens per second ≤ batch size × memory bandwidth ÷ model size, and notes
that a decode step for 32 requests reads the same weights as a step for one
([Together AI](https://www.together.ai/blog/llm-inference)).

**Schedule per iteration, not per request.** Orca introduced iteration-level scheduling: the
scheduler runs one model iteration on the current batch and then re-decides, so finished requests
leave and new ones join immediately. On GPT-3 175B it reported 36.9× the throughput of NVIDIA
FasterTransformer at the same latency
([Yu et al., OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/yu)). Anyscale measured
up to 23× throughput over naive serving with vLLM while also reducing median latency. The technique
goes by three names: continuous batching (vLLM, Anyscale), in-flight batching (TensorRT-LLM) and
iteration-level scheduling (the literature).

**Measure goodput.** DistServe defines goodput as the maximum request rate at which a target share of
requests (for example 90%) meets both a time-to-first-token and a time-per-output-token objective,
and argues a system can have high throughput and low goodput. Prefill and decode interfere when
batched together, so separating them onto different accelerators (*disaggregation*) let DistServe
serve 7.4× more requests or meet 12.6× tighter latency targets than the systems it compared against
([Zhong et al., OSDI 2024](https://arxiv.org/abs/2401.09670)). It also notes that per-token speed
only needs to beat human reading speed for chat.

**Providers sell the trade-off as tiers.**

- **Microsoft** offers standard (pay per token, no latency SLA), provisioned (per PTU per hour, with
  a defined latency target per model) and batch deployments, and recommends standard for variable or
  unpredictable traffic; provisioned deployments can spill over to standard at peaks
  ([Microsoft Learn](https://learn.microsoft.com/azure/foundry-classic/openai/concepts/provisioned-throughput)).
- **Google** runs pay-as-you-go on Dynamic Shared Quota, where a 429 signals temporary contention
  rather than a fixed quota and should be retried with back-off; Provisioned Throughput reserves
  capacity in generative AI scale units, and requests beyond it spill over to pay-as-you-go unless a
  header restricts them to dedicated capacity
  ([Google Cloud](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/provisioned-throughput/use-provisioned-throughput)).
  Google also offers flex and priority pay-as-you-go tiers.
- **AWS** offers on-demand (with cross-Region inference profiles that route across Regions for more
  throughput), Provisioned Throughput, and batch; inference profiles don't support Provisioned
  Throughput ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)).
  Latency-optimised inference is in preview for a few models.
- **OpenAI** offers flex (cheaper, slower, lower availability) and priority processing alongside the
  Batch API (via gateway documentation; not verified first-party here).
- **Anthropic** offers *fast mode* on some Opus models: up to 2.5× higher output tokens per second
  from the same model at premium pricing, with the gain in output speed rather than time to first
  token ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/fast-mode)). Anthropic's
  separate Priority Tier commitments are no longer sold (per gateway documentation quoting Anthropic;
  not verified first-party here).

"large", not as what you will get.

## Failure modes and antipatterns

- **Throughput benchmarks without latency percentiles.**
- **One pool for interactive and batch work**, so a back-fill job wrecks chat latency. Separate pools
  or priorities.
- **Retrying 429s without back-off** on shared capacity, which deepens the contention.
- **Provisioned capacity sized to the average**, so peaks spill over to pay-as-you-go anyway, or fail
  if spillover is disabled.
- **Ignoring output length.** Long answers hold batch slots and cache memory; cap `max_tokens` where
  you can ([2.1](../2-trade-offs/2.1-cost-quality-latency.md)).

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Service misses its latency commitments at peak | Operational resilience | Capacity sized to p95/p99 targets with headroom; load tests; spillover or fallback | Load-test reports; latency dashboards by percentile |
| Batch jobs starve interactive users | Operational resilience | Separate deployments, quotas or priority tiers | Quota configuration; incident history |
| Paying for idle reserved capacity | Cost management | Utilisation monitoring; review provisioned commitments against usage | Utilisation reports; commitment reviews |
| Spillover sends data to a region it may not go to | Data residency | Check spillover and cross-region routing scope against data classification | Deployment configuration; residency assessment |
