## What it is

An AI gateway is a reverse proxy that every model call in an organisation passes through. Applications
call one endpoint with one credential; the gateway decides which model and provider serve the request,
enforces who may use what and how much, and records what happened.

The problem it solves appears the moment there is a second team or a second provider. Without a
gateway, every application holds its own provider keys, implements its own retries, and reports its own
usage, so nobody can answer "what are we spending, on what, and who called which model?" A gateway
moves those concerns out of every application into one shared layer, in the same way API gateways did
for web services.

The providers describe the same responsibilities:

- Microsoft's AI gateway in Azure API Management authenticates callers, enforces per-consumer token
  limits, balances load across model endpoints with a circuit breaker, emits token metrics and supports
  semantic caching ([Microsoft Learn](https://learn.microsoft.com/azure/api-management/genai-gateway-capabilities)).
- AWS's reference architecture deploys an open-source gateway (LiteLLM) behind a single API in the
  OpenAI format, for usage tracking, cost management and governance across Bedrock and external
  providers ([AWS](https://docs.aws.amazon.com/solutions/multi-provider-generative-ai-gateway-on-aws/)).
- Google shows Apigee as an AI gateway with model-based routing across providers, fallback, Model Armor
  screening of prompts and responses, and a semantic cache
  ([Google Cloud](https://docs.cloud.google.com/apigee/docs/api-platform/fundamentals/build-ai-gateway)).
- Anthropic's enterprise guidance for Claude Code lists what a gateway provides: central
  authentication, usage tracking, budgets and rate limits, audit logging and model routing
  ([Anthropic](https://docs.anthropic.com/en/docs/claude-code/llm-gateway)).
- OpenAI ships no gateway, but its API shape has become the common interface that most gateways expose.

### What a gateway does

| Responsibility | What it means | Why it is AI-specific |
|---|---|---|
| **Unified interface** | One API format for every model and provider | Providers differ in request shapes and auth |
| **Authentication** | Apps authenticate to the gateway; the gateway holds provider credentials (or uses managed identities) | Removes provider keys from every app |
| **Token quotas and budgets** | Limits per team, app or user, in tokens per minute and spend per period | Cost and capacity are measured in tokens, not requests |
| **Routing** | Choose model and provider per request: by name, by rule, by cost, or by a learned router | See [2.1](../2-trade-offs/2.1-cost-quality-latency.md) |
| **Load balancing** | Spread traffic across deployments and regions; prefer reserved capacity first | Provider capacity is rationed per deployment |
| **Resilience** | Timeouts, retries with back-off, fallback chains, circuit breakers | Providers rate-limit and have outages |
| **Policy hooks** | Call input and output guardrails, PII redaction, content safety | One place to enforce policy for every app ([3.2](../3-components/3.2-input-guardrails.md), [3.12](../3-components/3.12-output-guardrails.md)) |
| **Caching** | Exact or semantic response caching | See [3.13](../3-components/3.13-caching.md) |
| **Telemetry and audit** | Tokens, cost, latency and errors per caller; optional prompt and response logging | Chargeback, capacity planning, compliance |

Two details matter more than they look. First, **count tokens, not requests**: one request can be ten
tokens or two hundred thousand. Azure's token-limit policy can even estimate prompt tokens before
forwarding, and reject a request that would exceed the limit without calling the model. Second,
**circuit breakers should respect the provider's back-off signal**: Azure's circuit breaker uses the
`Retry-After` header to decide how long to stop sending traffic.

### Routing modes

- **By name.** The caller asks for a model; the gateway maps it to a deployment. Simple, and lets you
  swap a deployment without touching apps.
- **By rule.** Route by caller, task type, data classification (sensitive data only to approved
  regions), or prompt size.
- **By prediction.** A learned router sends each request to the cheapest model likely to handle it
  (Azure's model router, Bedrock's Intelligent Prompt Routing). Measure it with evals; router accuracy
  decides whether it pays ([2.1](../2-trade-offs/2.1-cost-quality-latency.md),
  [lab 2.1](../../labs/2.1-cost-quality-latency/README.md)).
- **Fallback.** On error, timeout or rate limit, retry on another deployment, region or provider.

## When to use / when to avoid

| Use when | Avoid or defer when |
|---|---|
| More than one team, app or provider shares model access | One application calls one deployment: set limits on the deployment itself (Microsoft's guidance says the same) |
| You need chargeback, budgets or audit of who called which model | The gateway would add a hop in a latency-critical path without adding a control you need |
| You need failover across deployments, regions or providers | You can't operate it with the availability of the services behind it |
| Policy (guardrails, data residency) must apply to every app consistently | |

## Trade-offs

- **[2.1 Cost vs quality vs latency](../2-trade-offs/2.1-cost-quality-latency.md).** The gateway is
  where routing, caching and quotas turn cost policy into practice. It also adds a network hop; keep its
  overhead small compared with the model call.
- **Central control vs team autonomy.** A gateway makes the platform team a dependency of every AI
  feature. Self-service onboarding (keys, quotas, model catalogue) keeps it from becoming a bottleneck.
- **[2.4 Capability vs security](../2-trade-offs/2.4-capability-vs-security.md).** Logging prompts and
  responses helps audit and debugging, and creates a sensitive data store of its own.

## Limitation → mitigating pattern

| Limitation | Mitigating pattern |
|---|---|
| Provider keys scattered across apps | Gateway-held credentials or managed identities; per-app virtual keys |
| One team exhausts shared capacity | Token quotas per caller |
| Runaway spend | Budgets with alerts and hard stops |
| Provider outage or throttling | Fallback chains, circuit breakers, multi-region deployments |
| Inconsistent safety controls | Guardrail hooks enforced at the gateway |
| Single point of failure | Run the gateway redundantly across zones and regions |

## Numbers

| Figure | Value | As of | Source |
|---|---|---|---|
| Availability with fallback to an independent provider, each 99.5% available | ≈ 99.997% (derived: 1 − 0.005²), only if outages are independent; shared regions or shared upstream dependencies reduce this | — | Derived |
| Vendor claim for learned routing savings | up to 30% (AWS); up to 98% on research tasks (FrugalGPT) | 2024–2026 | See [2.1](../2-trade-offs/2.1-cost-quality-latency.md) |

The gateway's own availability caps everything behind it: a 99.9% gateway in front of a 99.997%
fallback pair yields at most 99.9%.

## Failure modes and antipatterns

- **Rate-limiting requests instead of tokens.** One caller with huge prompts still exhausts capacity.
- **Fallback to a model nobody evaluated.** A fallback that silently swaps in a weaker model trades an
  outage for a quality incident. Evaluate fallback models like primaries.
- **Fallback across a policy boundary.** Failing over to a provider or region your data may not go to.
  Routing rules must encode data classification and residency.
- **Retry storms.** Retries without back-off or circuit breaking amplify a provider's overload.
- **A gateway with weaker availability than the models behind it.**
- **Logging everything, forever.** Prompt and response logs inherit the sensitivity of the data in them.
- **Semantic caching across users.** A cached answer for one user's context served to another can leak
  data ([3.13](../3-components/3.13-caching.md)).

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Runaway cost or capacity exhaustion from abuse or bugs ("denial of wallet") | OWASP LLM10:2025 Unbounded Consumption ([OWASP](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/)) | Input size limits, token quotas per caller, budgets with alerts, timeouts, anomaly detection | Quota configuration; budget alerts and their history |
| Unapproved models or providers used | Third-party and model risk management | Model catalogue enforced at the gateway; deny by default | Allowed-model list; change history; blocked-request logs |
| Data sent to a region or provider it may not go to | Data residency and data protection | Routing and fallback rules keyed on data classification | Routing configuration; tests of fallback paths |
| Provider credentials leaked from apps | Secrets management | Credentials held only by the gateway; managed identities; rotation | Secret inventory; rotation records |
| Sensitive prompts and responses stored in logs | OWASP LLM02:2025 Sensitive Information Disclosure | Redaction, retention limits, access control on logs | Logging configuration; retention policy |
| No record of who used which model | Audit and accountability | Per-caller telemetry and audit logs | Usage reports by team, app and model |

## Cloud mapping

| | Azure | AWS | Google Cloud | Self-hosted / open source |
|---|---|---|---|---|
| Gateway | AI gateway in Azure API Management (also integrated with Microsoft Foundry) | Multi-Provider Generative AI Gateway guidance (LiteLLM on ECS/EKS); AgentCore Gateway (tools, agents and model routing across providers) | Apigee as an AI gateway | LiteLLM, Kong AI Gateway, Envoy AI Gateway, Portkey and others |
