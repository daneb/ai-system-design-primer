# 3.13 Caching: deep dive

Reference material for [3.13 Caching](../3-components/3.13-caching.md). Read that first.

## Prompt caching by provider

Every provider caches an exact prefix, but control, pricing and lifetime differ. Figures below are
from first-party documentation unless marked; they change with model generations, so check the
current page before relying on one.

- **Anthropic.** Mark the end of the cacheable prefix with `cache_control` breakpoints. A 5-minute
  cache write costs 1.25× the base input price, a 1-hour write 2×, and a cache read 0.1×
  ([Anthropic](https://docs.claude.com/en/docs/build-with-claude/prompt-caching)). The cache checks
  for hits up to 20 content blocks before a breakpoint; add more breakpoints for longer prompts.
  Secondary sources report automatic caching became the default in 2026 (not verified here).
- **OpenAI.** Automatic for prompts of 1,024 tokens or more; every response reports `cached_tokens`.
  A `prompt_cache_key` improves routing to the same cache for shared prefixes (OpenAI suggests keeping
  traffic per key to about 15 requests per minute). Retention is in-memory or extended up to 24 hours,
  priced the same; extended retention stores key/value tensors on GPU-local storage and so is not
  zero-data-retention eligible. Newer model families add explicit breakpoints and a cache-write rate
  ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)). Read discounts vary by
  model family (secondary sources cite 50–90%; not verified per model).
- **Google.** *Implicit* caching is on by default for Gemini on Vertex AI with a 90% discount on cached
  tokens and no storage charge. *Explicit* caching creates a named cache you reference, with a
  guaranteed discount (90% on Gemini 2.5 and later, 75% on 2.0), a default 60-minute lifetime you can
  change, and storage charges; the minimum is 2,048 tokens on Vertex AI. Explicit caches can trigger
  additional implicit caching, so disable implicit caching if retention matters
  ([Google Cloud](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)).
- **Microsoft.** Azure OpenAI caches automatically for supported models; cached reads are discounted on
  standard deployments and up to 100% on provisioned deployments, with extended retention up to 24
  hours ([Microsoft Learn](https://learn.microsoft.com/azure/foundry/openai/how-to/prompt-caching)).
- **AWS.** Bedrock supports implicit (best-effort) and explicit caching with cache checkpoints; lifetimes
  of 5 minutes, or 1 hour for some newer Claude models, and per-model minimums (via secondary
  sources quoting the Bedrock guide; not verified here).

## Semantic caching

Microsoft's API Management semantic cache looks up previous responses by vector similarity above a
threshold and warns that, because matching is by similarity rather than exact match, it can return
responses that are incorrect, outdated or unsafe for the current request. Its guidance: start with a
strict threshold, ignore system messages when comparing, partition entries by user or group with
`vary-by`, add a content-safety check, and rate-limit behind the cache in case it is unavailable
([Microsoft Learn](https://learn.microsoft.com/azure/api-management/llm-semantic-cache-lookup-policy)).
Google's Apigee AI gateway offers a semantic cache too ([3.1](../3-components/3.1-ai-gateway-and-router.md)).

The primer's view is stricter than the vendors': response caching by similarity is a correctness risk,
not just a tuning problem ([Lab 3.13](../../labs/3.13-caching/README.md)).

## Failure modes and antipatterns

- **Variable content at the top of the prompt** (timestamps, user names, request IDs).
- **Re-ordering tools or documents between calls**, which changes the prefix.
- **Assuming a hit rate** instead of reading the cached-token counts every response returns.
- **Load balancing across replicas or regions without affinity**, so each replica re-processes the prefix.
- **Semantic caching of personalised or numeric answers.**
- **A shared response cache without a user or tenant key.**

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Wrong answer served from a similarity cache | Model risk; OWASP LLM09 Misinformation | Restrict semantic caching to low-stakes content; strict thresholds; evaluate false-hit rate | Cache scope decision; false-hit test results |
| One user's answer served to another | OWASP LLM02 Sensitive Information Disclosure | Partition response caches by user or tenant; never cache personalised answers | Cache key design; test showing isolation |
| Cached prompts retained beyond policy | Data protection; zero-data-retention commitments | Choose retention settings to match policy; disable implicit caching where required | Provider settings; data-retention assessment |
| Stale answers after source changes | Data quality | Short lifetimes; invalidate on source updates | Invalidation design; freshness monitoring |
