# 3.14 Asynchronism: deep dive

Reference material for [3.14 Asynchronism](../3-components/3.14-asynchronism.md). Read that first.

## Where the sources agree

**Retries need backoff, jitter and idempotency.** The Amazon Builders' Library sets out the standard
toolkit: timeouts, retries and backoff; jitter so clients don't retry in sync; and the warning that
APIs with side effects aren't safe to retry unless they are idempotent, because a timeout doesn't mean
the side effect didn't happen
([Brooker](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter)). Amazon's
preferred idempotency mechanism is a unique caller-provided request identifier in the API contract,
recorded atomically with the mutation
([Featonby](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)).

**Batch at half price.**

- **Anthropic:** Message Batches charge 50% of standard prices; a batch holds up to 100,000 requests
  or 256 MB; most finish within an hour, and requests not processed within 24 hours expire; results
  stay available for 29 days; prompt caching works within batches; use `custom_id` to match results
  ([Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/batch-processing)).
- **OpenAI, Google, Azure, AWS:** batch at 50% off with a 24-hour window or target
  ([OpenAI](https://developers.openai.com/api/docs/guides/batch),
  [Google](https://ai.google.dev/gemini-api/docs/batch-mode),
  [Azure](https://learn.microsoft.com/azure/ai-foundry/openai/how-to/batch)); AWS Bedrock prices batch
  50% below on-demand for selected models ([AWS](https://aws.amazon.com/bedrock/pricing/)). Checked 2026-11-02.

**Background requests.** OpenAI's background mode runs a long Responses request asynchronously; you
poll until it leaves the queued or in-progress state, can cancel it, and can resume a dropped stream.
Because it stores response data for roughly ten minutes to allow polling, it isn't zero-data-retention
compatible ([OpenAI](https://developers.openai.com/api/docs/guides/background)).

**Durable execution moved into the clouds.** Temporal popularised the model: workflows are
deterministic code, and anything non-deterministic (a model call, an API request) runs as an
*activity* whose result is recorded durably, so a restarted workflow replays from history. Azure
Durable Functions offers the same model on Azure, AWS Step Functions orchestrates long workflows with
retries and human waits, and AWS Lambda durable functions (late 2025) checkpoint each step of runs
lasting up to a year, with AWS samples covering prompt chaining, human review, LLM-as-judge and agents
([AWS samples](https://github.com/aws-samples/sample-ai-workflows-in-aws-lambda-durable-functions)).
A known pitfall is large model payloads bloating workflow history; teams store payloads externally and
keep references (per a secondary source).

**Rate-limit signals differ.** Providers return 429 when you exceed your limits, usually with a
`retry-after` hint; Anthropic also returns 529 when its own capacity is overloaded, which is a reason
to fail over rather than wait (via secondary sources; not verified first-party here). Google's shared
pay-as-you-go returns 429 for temporary contention and recommends exponential backoff
([2.7](2.7-throughput-vs-latency.md)).

## Failure modes and antipatterns

- **Synchronous HTTP for multi-minute tasks**, so load balancers time out and the work is lost.
- **Retrying non-idempotent tool calls** after a timeout.
- **No dead-letter queue**: poison requests retry forever.
- **Fire-and-forget batches** whose expired requests nobody notices.
- **Storing full prompts in workflow history**, bloating it and spreading sensitive data.
- **One queue for interactive and bulk work**, so a back-fill delays users.

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Duplicate side effects from retries (double payment, duplicate message) | Operational risk | Idempotency keys on every mutating tool; durable workflow state | Tool API design; duplicate-detection tests |
| Lost or silently failed work | Operational resilience | Durable queues; dead-letter queues with alerting; batch expiry monitoring | DLQ dashboards; incident records |
| Retry storms extending outages | Operational resilience | Backoff with jitter; retry budgets; circuit breakers at the gateway | Client configuration; load-test results |
| Batch and background data kept beyond policy | Data protection | Choose retention settings; delete results after use | Retention configuration; deletion logs |
