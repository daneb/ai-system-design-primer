## What it is

AI security is ordinary application security plus a few new problems. Most of the controls are old
ones: identity, least privilege, encryption, logging, dependency hygiene. What is new is that the
model mixes instructions and data in one stream, acts on whatever it reads, and produces output that
nobody wrote. That makes the boundaries in the diagram above leak in ways a normal web app's don't.

This is a hub section. It gives you a threat model and points to the sections that hold each control:
input guardrails ([3.2](../3-components/3.2-input-guardrails.md)), output handling ([3.12](../3-components/3.12-output-guardrails.md)),
the gateway ([3.1](../3-components/3.1-ai-gateway-and-router.md)), and the capability trade-off for agents
([2.4](../2-trade-offs/2.4-capability-vs-security.md)).

### Start with scope: what do you own?

AWS's Generative AI Security Scoping Matrix sorts use cases into five scopes by ownership: a consumer
app, an enterprise app with AI features, your app on a pre-trained model, a fine-tuned model, and a
model you trained yourself ([AWS](https://aws.amazon.com/blogs/security/securing-generative-ai-an-introduction-to-the-generative-ai-security-scoping-matrix/)).
The scope decides which controls are yours. Most bank systems are Scope 3: you call a hosted model and
own everything around it (prompts, retrieval, tools, data, logs). Google's SAIF makes the same split
between model creators and model consumers ([SAIF](https://saif.google/secure-ai-framework)).

### Walk the boundaries

**1. Prompts.** Users can try to override instructions (direct injection) or extract the system prompt
(LLM07). Treat the system prompt as public: put no secrets or access rules in it. Detection lives in
[3.2](../3-components/3.2-input-guardrails.md).

**2. Untrusted content.** Anything the model reads that an outsider can influence can carry
instructions: web pages, emails, uploaded files, other agents' outputs, and tool descriptions. This is
indirect injection, the top entry on OWASP's list and, per Microsoft, one of the most widely used
techniques in AI vulnerabilities reported to it
([MSRC](https://www.microsoft.com/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)).
Detectors help, but adaptive attacks broke 12 published defences, most at over 90% success
([Nasr et al., 2025](https://arxiv.org/abs/2510.09023)). The durable answer is architectural: limit
what an injected model can do ([2.4](../2-trade-offs/2.4-capability-vs-security.md)).

**3. Retrieval and data.** RAG creates a second copy of your documents, often without their access
controls. If the index ignores who may read what, the model will happily quote a document to someone
who could never open it. Filter by the caller's permissions at query time
([3.6](../3-components/3.6-vector-stores.md)), not after generation. OWASP lists vector and embedding weaknesses
(LLM08), including poisoned documents and leaks across tenants. Anyone who can edit an indexed source
can plant instructions in it.

**4. Tool calls.** This is where text becomes action. Three rules recur across OWASP, Google, AWS and
OpenAI:

- **Authorise outside the model.** Check every call and its arguments in code or a policy engine
  (complete mediation), never by asking the model whether it is allowed
  ([OWASP LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). AWS AgentCore Policy
  does this with Cedar rules at the gateway
  ([AWS](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-getting-started.html)).
- **Act as the user, not as the system.** Propagate the real user's identity and permissions to every
  backend tool (OAuth on-behalf-of, short-lived scoped tokens). Google's SAIF guidance says agents
  should do exactly this ([Google Cloud](https://cloud.google.com/blog/products/identity-security/cloud-ciso-perspectives-practical-guidance-building-with-saif/));
  OWASP's agentic list names the failure Identity and Privilege Abuse (ASI03).
- **Gate the irreversible.** Payments, deletions, external messages and access grants need human
  approval or a hard limit ([2.4](../2-trade-offs/2.4-capability-vs-security.md)).

Model output that reaches a browser, shell, SQL engine or another system is untrusted too: encode,
validate and sandbox it (LLM05, [3.12](../3-components/3.12-output-guardrails.md)). Code execution belongs in a
sandbox with both filesystem and network isolation; Anthropic notes that either one alone leaves an
escape route ([Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)).

**5. Supply chain.** Three new kinds of dependency:

- **Model files.** Pickle-based formats can run code when loaded; researchers have repeatedly found
  malicious models on public hubs, including about 100 on Hugging Face in one 2024 scan
  ([JFrog](https://jfrog.com/blog/data-scientists-targeted-by-malicious-hugging-face-ml-models-with-silent-backdoor/)). Prefer safetensors, pin by digest, and verify signatures. The
  OpenSSF model-signing project reached v1.0 in April 2025, using Sigstore
  ([Sigstore](https://blog.sigstore.dev/model-transparency-v1.0)).
- **Tool servers (MCP).** A tool's description is read by the model, so a malicious one can carry
  instructions (tool poisoning), and a server can change its definitions after you approved them (a
  rug pull). Invariant Labs documented both in April 2025
  ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)). Review, pin and re-approve on change.
  [Lab 3.17](../../labs/3.17-security/README.md) shows pinning catching a rug pull while a keyword
  scanner misses a poisoned description written in plain prose.
- **Prompts, datasets and evaluation sets.** Version them, review changes, and control who can edit
  them, like code.

**6. Telemetry.** Prompts, retrieved passages and outputs end up in logs and traces, often with
personal data and often shipped to a third-party tool. Mask before logging, restrict access, and set
retention ([3.16](../3-components/3.16-observability.md)). The same applies to provider-side retention: know what
your provider keeps and for how long.

**Consumption.** Attackers can run up your bill or exhaust capacity (LLM10). Token quotas and rate
limits at the gateway are the control ([3.1](../3-components/3.1-ai-gateway-and-router.md)).

### Test like an attacker

Static test sets overstate robustness; the attacker moves second. Red-team before launch and after
each significant change (model, prompt, tools), with automated tools for coverage and people for
depth. Microsoft's open-source PyRIT powers the AI Red Teaming Agent in Foundry, which now covers
agent risks such as prohibited actions and sensitive-data leakage
([Microsoft](https://devblogs.microsoft.com/foundry/assess-agentic-risks-with-the-ai-red-teaming-agent-in-microsoft-foundry/)).
NVIDIA's garak is an open-source probe scanner. Feed confirmed findings into your eval suite as
regression cases ([3.15](../3-components/3.15-evals.md)).

## When it matters most

Every system needs the basics. The bar rises sharply when a system reads content from outside the
organisation, holds personal or confidential data, can act on other systems, or serves many tenants
from one index. Systems that are internal, read-only, and grounded in a curated corpus can lean on
ordinary controls.

## Trade-offs

- **Deterministic vs probabilistic controls.** Policy engines, scopes and sandboxes give guarantees
  but limit capability. Classifiers keep capability but only lower rates. Microsoft and Google both
  recommend layering the two.
- **Approval vs autonomy.** Human approval stops harm but costs time and causes approval fatigue.
  Sandboxing safe actions lets you approve fewer, more meaningful ones.
- **Visibility vs privacy.** Full prompt logging helps incident response and evals, and creates a new
  store of sensitive data.
- **Third-party tools vs control.** Public tool servers and models save time and import someone
  else's security posture.

## Limitation → mitigating pattern

| Limitation | Pattern |
|---|---|
| Models can't tell instructions from data | Rule of Two, dual LLM, plan-then-execute ([2.4](../2-trade-offs/2.4-capability-vs-security.md)) |
| The model can't be trusted to enforce access | Authorisation in code or a policy engine; on-behalf-of identity |
| Retrieval bypasses document permissions | Permission filters at query time; per-tenant indexes |
| Output can carry code, links or markup | Encode and validate before use; block outbound images and links ([3.12](../3-components/3.12-output-guardrails.md)) |
| Tool definitions change silently | Pin, diff and re-approve |
| Defences look strong on static tests | Adaptive red teaming; findings become regression evals |

## Failure modes and antipatterns

- **Secrets or access rules in the system prompt.** Assume it will leak.
- **One service account for every user.** An injected agent then reaches everyone's data.
- **A RAG index without document permissions.**
- **Treating vendor guardrails as the security boundary.**
- **Auto-approving tool servers** and never re-checking their definitions.
- **Loading model files with `pickle`** from an unverified source.
- **Logging full prompts to a third party** without masking or a retention rule.
- **Red-teaming once at launch** and never after a model or prompt change.

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Indirect prompt injection leading to data theft or actions | OWASP LLM01; ASI01 Agent Goal Hijack | Rule of Two review per agent; detection on untrusted content; human approval for high-impact actions | Agent capability inventory (A/B/C); approval logs; red-team reports |
| Agent acts beyond its mandate | OWASP LLM06; ASI02 Tool Misuse | Minimal tools and scopes; policy checks on every call and argument; rate limits | Tool inventory with risk ratings; policy source and test results; denied-call logs |
| Agent uses broader rights than the user has | ASI03 Identity and Privilege Abuse | On-behalf-of identity; short-lived scoped credentials | Identity flow design; token scopes; access reviews |
| Unauthorised disclosure through retrieval | OWASP LLM02, LLM08 | Permission-aware retrieval; tenant isolation; masking | Permission-filter tests; cross-tenant test results |
| Unsafe output reaches downstream systems | OWASP LLM05 | Encoding, validation, sandboxed execution | Validation rules; sandbox configuration; test cases |
| Compromised model, package or tool server | OWASP LLM03; ASI04 | Signed models in safe formats; pinned digests; tool pinning and re-approval | Software and AI bill of materials; signature checks in deployment logs |
| Sensitive data in logs and traces | OWASP LLM02; data protection law | Masking before logging; access control; retention limits | Logging configuration; redacted samples; retention policy |
| Cost or capacity exhaustion | OWASP LLM10 | Token quotas and rate limits at the gateway | Quota configuration; alerts |
| Defences degrade unnoticed | Model risk management; NIST AI 600-1 | Red teaming at launch and on change; regression evals | Red-team schedule and findings; eval history |
