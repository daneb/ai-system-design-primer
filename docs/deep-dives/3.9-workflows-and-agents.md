## Where they agree

- **Start simple, add autonomy only when it pays** (all five; see [2.2](2.2-determinism-vs-autonomy.md)).
- **Start with one agent.** Google and OpenAI both advise a single agent before multi-agent systems.
- **Agents need ground truth and stopping conditions.** Anthropic: agents should get ground truth from
  the environment at each step and use stopping conditions such as a maximum number of iterations.
  OpenAI's SDK sets a maximum number of turns; Microsoft's group chat has a maximum-rounds setting.
- **Human checkpoints for high-risk actions.** OpenAI's tool risk ratings and Microsoft's
  approval-required tools ([2.4](2.4-capability-vs-security.md)).

## Where they differ

- **Handoffs vs manager.** OpenAI frames these as the two broadly applicable multi-agent patterns:
  a manager keeps control and calls specialists as tools; a handoff transfers ownership of the
  conversation. OpenAI's guide uses a manager when one agent should keep control and stay the user's
  point of contact, and handoffs when no central synthesis is needed, as in triage. It also advises
  getting the most from a single agent before splitting.
- **Frameworks.** Anthropic warns that frameworks can obscure prompts and responses and suggests
  starting with direct API calls; Microsoft, AWS (Strands) and Google (ADK) ship frameworks and
  managed agent runtimes.
- **Event-driven framing.** AWS maps agent patterns onto event-driven architecture (sagas, choreography,
  dynamic dispatch), which suits teams already running those systems.

## Tool design

Anthropic's guidance treats the agent–computer interface like a human–computer interface: clear tool
names and descriptions, examples, edge cases, and formats close to what the model has seen in text;
test how the model uses tools and iterate. OpenAI recommends standardised tool definitions reused across
agents. Fewer, sharper tools beat many overlapping ones; ambiguous tools are a common cause of wrong
calls (and see tool poisoning in [3.17](3.17-security.md)).

## Failure modes and antipatterns

- **No step cap or budget.**
- **Agent judges its own success** with no external check.
- **Tool sprawl:** dozens of similar tools, so the model picks the wrong one.
- **Context bloat** from accumulating every tool result ([3.3](../3-components/3.3-context-engineering.md)).
- **Handoff loops**, where agents pass a conversation back and forth.
- **Framework magic** nobody on the team can debug.

## Risk and controls

| Risk | Reference | Control | Evidence an auditor would ask for |
|---|---|---|---|
| Agent takes harmful or unintended actions | OWASP LLM06; ASI02 | Least-privilege tools; approvals for high-risk actions; policy checks on tool calls | Tool inventory with risk ratings; approval logs |
| Runaway loops and cost | OWASP LLM10 | Step caps, budgets, timeouts | Configuration; cost alerts |
| Unexplainable decisions | Model risk; audit | Trace every step, tool call and result ([3.16](../3-components/3.16-observability.md)) | Trace retention; sample reviews |
| Inconsistent outcomes | Model risk | Evaluate repeated trials (pass^k) | Eval reports |
